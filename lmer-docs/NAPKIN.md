# NAPKIN.md — Shared Team Working Notes

Napkin is the team's shared brain: in-flight working notes, organized by org,
visible to the whole team. This file tells agents how to use it.

## Where to write

Write to `$LMER_NAPKIN_PATH/{org}/` (equivalently `~/napkin/{org}/`), choosing
the org directory the note belongs to:

- `org-a/`, `org-b/`, `lmer/`, `other/`, and similar — use the org directories
  your napkin repo already defines (its own AGENTS.md lists them).

`$LMER_NAPKIN_PATH` is set in every session and resolves correctly whether
napkin is a separate repo (`/napkin`) or a subdir of the work repo
(`/work/napkin`). Never hard-code either path — always use `$LMER_NAPKIN_PATH`
or `~/napkin`.

## What belongs here

- Analysis notes, investigation findings, design sketches, and synthesis that
  the team should be able to read later — **not** per-task worklogs (those go to
  the work repo via `work log`).
- Draft material. Treat existing notes as drafts, not authoritative; the
  authoritative docs live in the GitLab wiki.

## File naming

- Name files by **topic**, not by date: `qfx5220-channelization.md`, not
  `2026-06-22-notes.md`.
- Date-prefix only when the date is part of the artifact's identity
  (postmortems, meeting notes, incident timelines).
- Keep each note scoped to its topic. Don't append tangential findings to an
  unrelated file — start a new one.

## Before you write

Read the relevant org directory first — there may be related notes worth
cross-linking. When you synthesize across multiple notes, cite the sources you
drew from (e.g. `see org-a/rate-limiting-analysis.md`).

## How to push

Run `work commit`. It captures napkin in **both** modes:

- Subdir mode: napkin lives under the work repo; `work commit` stages and
  pushes the `napkin/` subdir alongside the worklog commit.
- Separate-repo mode: `work commit` additionally commits the napkin repo,
  integrates the remote with `pull --rebase`, and pushes with retries.

In either mode a napkin failure is a warning and never blocks the worklog
commit.

## Never write here

- Credentials, API keys, tokens, or PII.
- Contractual or legal material.
- AI attribution lines ("Generated by …", `Co-Authored-By`, etc.).
