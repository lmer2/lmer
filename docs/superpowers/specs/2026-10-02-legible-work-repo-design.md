# Specification: a human-legible lmer work repo (synthesized design, 2026-10-02, revision 2)

Base: runtime `origin/schema-v2` at `4463552a` (read in a dedicated worktree); first consumer a personal schema-2 work repo. Starting point is the **concurrency** design (favoured by two judges), with the grafts the judges marked and that survived their defect lists: minimal's clock-free rows, exact-`_runs` project mapping and small validator footprint; legibility's human-facing row, preambles, redaction and legacy-branch label application; schema's exact doc/test-pin inventory and the no-mtime ordering rule. Revision 2 folds in the critic round: every important finding changed the design (hand-text marker screen, timestamp coercion, the handler as the normal concurrent path, `GIT_EDITOR` in the base git env, tracked-or-staged rendering, launch-identity isolation, deep-chain performance), the cheap minors are folded, and the three findings argued against are in "Rejected findings". Every mechanism below was re-read in the source at 4463552a; the contested git behaviours were re-run in a sandbox on git 2.55.0 (results cited inline); the deep-chain benchmark was run today (`scratchpad/repair/chain_bench.py`). Map citations are `understanding.md §n`.

## Deviations from the brief

1. **R5 — where `active`/`stale` appear.** The README's rows never carry a clock-derived word; `open` plus the `last activity` date carry R5's two separate facts ("no recorded sign-out" and "quiet since `<updated>`"), and `work sessions` renders the full five-word vocabulary with the validator's 14-day constant. Evidence: R2 requires each line to be a pure function of its record so that concurrent regenerations differ only on changed records; a clock word flips without any record change, forces a textual conflict on a row neither writer touched, and — the decisive point — reads `active` indefinitely in any project nobody pushes to again, which is exactly the dormant-project case the brief's headline symptom describes; the house style forbids clock reads in renderers (map §11.0 §13, `run_state.py:2413-2417`) and §11.D asks for the two facts to be kept apart. **Cost of overruling, stated plainly:** passing `now` at the one README call site is a one-argument change, but the exact-compare freshness oracle then stops working (an `open` row becomes `stale` after 14 days with no record change, so every clean clone reports `index.readme-stale`), so an overrule also requires either a masking step in the validator (re-render both sides with `now=None` before comparing) or giving up exactness; and the rows stop being pure functions of their records (map §11.A2 hotspot).
2. **R1 — root link spelling.** Root rows link `[name](name/)` rather than `name/README.md`. Evidence: GitLab 19.2.6 renders a directory's README below its file list (`tree_content.vue` L65/L206, map §10.2 (1)), so the directory link shows the README **and** the directory, and it never redirects to the repo root with a "did not exist" notice (MR !224639, map §10.5) for a project whose README has not been generated yet. One token to change if the literal file link is wanted.
3. **R1 — "byte for byte" on the first append.** A markerless README gets the block appended as `existing.rstrip("\n") + "\n\n" + block`, a one-time normalisation of the hand text's trailing newlines; every later splice replaces the marked span inclusively and leaves everything before the start marker and after the end marker untouched. The conflict handler's hand-text comparison uses the same normalisation.

Everything else follows R1–R8 and the non-negotiables as written. Axis C's "freshness fingerprint line" is an open axis, not a ruling; it is resolved against (see Decisions log).

## Rejected findings

1. **"Group by slug so concurrent first pushes in different slugs insert at different lines."** Rejected. After R3 every plain project session of a project shares the bare taskdef slug (`chat`), so in exactly the busiest group concurrent pairs are same-slug and would still insert at the same line; the shared repo's record population is dominated by few task types per project (map §9, slug tokens), so slug headings would add structure without separating the conflicting inserts. Any sorted single-file index puts near-simultaneous starts on adjacent lines; the remedy is a handler that is correct on the normal path, which this revision makes load-bearing (Decisions A, task 3), not a layout change. The brief's axis C alternative is recorded as considered and not taken.
2. **"Refuse `--name`/`--goal` combined with `--exec` (exit 2)."** Replaced by a host note, not a refusal. The brief's axis E explicitly contemplates `--exec` runs that call `work session-start` themselves, and `clone_and_exec` executes whatever command the user passes (`clone_and_exec.py:3007-3009`), so the flags are not inert by construction, only by the usual command. `--no-task` (no run context at all) is refused; `--exec` prints `ℹ️  --name/--goal are recorded by work session-start; this --exec command must run it for them to apply`.
3. **"Pin the `rebase --skip` fallback with an intercept that makes `--continue` fail with 'No changes'."** Replaced by deleting the fallback (the finding offered both). The merge backend's `commit_staged_changes` drops a pick that resolution emptied and `rebase --continue` reports success (verified on git 2.55 by two sandboxes; the image ships 2.52; the floor is 2.26, where the merge backend became the default); the live behaviour is pinned by a real-git test (an emptied replay completes and nothing is left in `rebase-merge`), and any other `--continue` failure returns `False` into the existing abort.

## Summary

One new module (`work_repo/project_index.py`) turns a project's run records into a deterministic Markdown block and splices it between `<!-- lmer:index:start -->` and `<!-- lmer:index:end -->` in `<project>/README.md`, preserving every byte outside the markers (trailing newlines excepted on the first append). Three thin callers share it: the locked publication choke point (regenerate the touched projects' blocks from the records the commit will contain and stage them with the record; resolve a rebase conflict confined to those blocks by regenerating from the merged tree and continuing; restore the README's bytes when staging is refused; sweep a crash-left generated README into the next push), the validator (two advisory codes computed by re-rendering), and `lmer-schema index PATH [--write]` (backfill of every project README and the root README, the only writer of the root block). Rows are clock-free functions of their own record, in a stable order, so git's three-way merge of two regenerations is the fresh render whenever it is clean — and because concurrent writers in one project almost always touch adjacent lines, the in-rebase regeneration is the normal path under load, built and tested as such.

The rest of the brief lands in the same MR: local-path targets export an empty `LMER_TASK_TARGET` so every slug copy yields the bare taskdef (`chat`), with a warning when a continuation's source was filed under `chat-.`; `lmer --name/--goal` carried flag-only into the container and applied once at session start, isolated so they can never refuse a session; a one-line nudge on every durability push while `name` is null; the schema-2 `work sessions` rendering fix with the derived five-word vocabulary computed where `now` already lives; two `index.*` validator codes and the SCHEMA.md rows, check-code table entries and changelog fragment the change process requires. Records are never written by any of it; schema stays 2; `derive_slug` and its mirrors do not change; existing `_runs/chat-./` groups stay where they are.

## Architecture

A pure kernel produces one `RecordSummary` per execution from lock-free reads of `state.yaml` (a fast reader that cuts out the nested `context:` block), `events.jsonl` and (only when both `name` and `goal` are null) `log.yaml`, over the resolvers' own walk (`run_state._record_scan`, `run_state.py:562-608`), filtered by an injected "will this record be in the commit" predicate, renders a block with no clock, counts or timestamps of generation, and splices it into whatever README text exists. The kernel imports nothing from `lmer_schema`; `work_repo.git_ops` calls it under the checkout lock immediately before staging and inside a paused rebase, with the tracked-or-staged predicate from one `git ls-files` per project; `lmer_schema.checks.index_links` calls its read-and-render half (write-free, git-free) with the runner's `manifest` and project list; `lmer_schema.cli` calls its plan-and-write half under `work_mutation`, with the tracked predicate when the root is a git checkout. The host CLI changes are independent of the kernel: one exported string (`LMER_TASK_TARGET`) and two flag-only variables.

2. **New, before any failure print:** if no `rebase-merge`/`rebase-apply` state exists (a transport failure) → the existing `_git_failure` and return. Otherwise `_continue_past_index_conflicts`, which returns `False` (so the existing print and abort run unchanged) when: `git diff --name-only -z --diff-filter=U` is empty; any unmerged path fails `_is_index_rel`; for any conflicted README stage 2 or stage 3 is missing (delete/modify), either side's markers are malformed, `block_format(stage2) > FORMAT` (a newer runtime wrote upstream's block; this runtime must not downgrade it), or `strip_block(stage2) != strip_block(stage3)` (a human edited the hand text on both sides — a human's conflict, WORK-REPO-SAFETY.md:75-78).
3. Otherwise, per conflicted README: the paused worktree holds upstream's tree plus the non-conflicting hunks of our commit (our own record files; single-writer, so they never conflict), and the index already holds our commit's record files; `block = render_project_block(scan_project(project_dir, include=tracked_record_filter(repo, rel)))` (untracked sibling dirs that remain visible in the worktree are excluded); write `splice_block(stage2_text, block, heading)` (upstream's hand text, fresh block); `git add -- <rel>`.
4. `git -c core.editor=true -c sequence.editor=true rebase --continue` with the base env's `GIT_EDITOR=true`/`GIT_SEQUENCE_EDITOR=true` (an exported `GIT_EDITOR` would otherwise win and leave the rebase paused — critic probe 4). A replay that regenerates to upstream's bytes is dropped by `--continue` itself (git ≥ 2.26). Any non-zero exit → `False`.
5. If the rebase stops again (another unpushed local commit replays onto a changed README), loop; bound `INDEX_CONFLICT_ROUNDS` (a bound on our own unpushed commits, normally one); exhausted or any non-index stop → `False` → the existing `❌` print and `rebase --abort` (`:1034-1043`) restore the pre-pull branch and reapply the autostash; local commits retained.
6. On success (no rebase state left) → `True` → `↻ regenerated project index on the merged head`, the unchanged autostash sanity check (`:1045-1056`; git reapplies the autostash when the rebase completes, "Applied autostash." in the sandbox), `check_commit_ready` (`:1057`), `rev-parse HEAD`, push (`:1063`), `_verify_published` (`:1065`). A rejected push loops (`:1066-1077`), bounded by `PUSH_RETRIES = 3` as today; the handler adds no attempt, it turns what would have been an abort into a push.
7. When the pull merges cleanly (edits separated by at least one unchanged row), each side's hunk against the common base is exactly its own records' rows (rows are pure functions of records both sides read from identical published bytes, in an immutable order), so the merged file is the render of the merged record set and no amend is needed. Under concurrent sessions in one project this is the exception: two new rows, or a new row beside the previously newest row's `last activity` change, are adjacent hunks and conflict.

Sandbox facts the handler relies on (git 2.55.0): tracked dirty sibling files are autostashed and invisible during the pause; untracked sibling record dirs remain visible and are excluded by the tracked filter.

- **Schema stays 2.** `<project>/README.md` and `README.md` are content namespace to runtime 4463552a (`layout.py:331`, 451-464; SCHEMA.md:148-150, :676, :696): no writer touches them, no reader reads them, the old validator registers no code for them. `list_sessions`' `stop_reason`/`state` keys and the `--json` fields are additive to a listing, not to a document; `LMER_RUN_NAME`/`LMER_RUN_GOAL` are unknown env to old containers and ignored; an empty `LMER_TASK_TARGET` is the already-documented no-target path (RUN-STATE.md:655-656).

## Index format

Block grammar (project):

```
<!-- lmer:index:start -->

## Runs

One row per execution record under `_runs/`, newest first — rendered by lmer from each record's own `state.yaml`, `events.jsonl` and `log.yaml` on every work-repo push and by `lmer-schema index --write` (lmer index format 1). States: **closed** = status complete or archived · **waiting on question** = stopped on a recorded question · **ended, not closed** = in progress with a recorded session end · **open** = in progress with no sign-out recorded; the last-activity column is the date the record last changed. Nothing here ever ends a run. Edit this file outside the markers only.

| started (UTC) | run | state | last activity | record |
|---|---|---|---|---|
| <rows> |

<!-- lmer:index:end -->
```

Rules:

- **run**: `[<label>](<dir_rel>/)`, prefixed `_(unnamed)_ ` when the label is derived; label = `name`, else the goal's first non-empty line, else the first `log.yaml` message, else `(unnamed)`; `flatten` applies environment-independent redaction (`redact_secrets(text, secret_values=[])`: token shapes and URL userinfo, never the renderer's env — `work goal`/`work name` already redact at write time, `cli.py:1588-1611`, `:2742-2744`), drops control characters, collapses whitespace, escapes `\ | [ ] ` < &`, cuts at the last space at or after 40 characters (else hard) and appends `…`; a continuation appends `· continues [<uid8>](<source_rel>/)` (plain `` `<uid8>` `` when the source path has no `_runs/` component). Links are spelled `_runs/<slug>/<dir>/` relative to the README (map §10.2 (3)); never `./`, `.` or `x/../` (issue #368767); path segments URL-quoted with `safe="/-._~"`.
- **state**: `display_state(now=None)`; precedence `unreadable` → `closed` (status complete or archived) → `waiting on question` (stop_reason question) → `ended, not closed` (in-progress and `signed_out is True`) → `open`; suffix ` (<stop_reason>)` for `yield`, `critical_error`, `aborted`; suffix ` · phase <phase>` when a phase is recorded.
- **started (UTC)** / **last activity**: `session.started_at` else `created`, and `updated`, parsed and rendered in UTC as `YYYY-MM-DD HH:MM` (a `+02:00` stamp is converted); an unparseable stamp is printed raw, cut to 16 characters; missing → `—`.
- **record**: `` `<slug>` · `<id>` `` — a 32-hex uid shown as its first 8 characters, a legacy timestamp id whole, `—` for a flat record (whose link is `_runs/<slug>/`).
- Order: `sort_key` descending on the parsed UTC instant (immutable inputs: an existing row never moves when a sibling is added, whatever the stamp's offset or spelling), unparseable stamps after parseable ones, missing last; dir name descending as tiebreak; never mtime.
- Membership: what the walk finds (`.new-*` seeds, dot-dirs, `archive/`, session dirs without a state file excluded, `run_state.py:562-608`, `:500-523`) intersected, when a git checkout is the source, with records whose state file is tracked or under a path the commit stages.
- Unreadable `state.yaml`: `| — | [<dir>](<dir_rel>/) | unreadable | — | `<group>` · `<id>` |`.
- Zero records: the table is replaced by `_No run records yet._`.
- Nothing volatile: no generated-at, no totals, no counts, no fingerprint. Size ≈ 250 B/row → 2,000 rows ≈ 500 KB, under GitLab's 2 MB collapse limit (`server_side.rb` L9-10); no cap (the cleaner's archive contract is the lever).
- A blank line follows the start marker and precedes the end marker (the HTML comment can never swallow the table under CommonMark's HTML-block rule). No generated line can start with seven identical `<`, `=`, `>` or `|`.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| The conflict handler, now the normal concurrent path, leaves a rebase half done | every exit other than success returns `False` into the existing `rebase --abort`; `check_commit_ready` at the top of the next attempt refuses any residue; `GIT_EDITOR`/`GIT_SEQUENCE_EDITOR` pinned in the base env; race tests (two and three writers, adjacent rows, failing editor, emptied replay, newer-format upstream) assert no `rebase-merge`/`rebase-apply` and an empty `ls-files --unmerged` |
| Heavy concurrency exhausts `PUSH_RETRIES` on a shared-repo project | unchanged bound and failure mode (local commit retained, next push retries); the handler converts aborts into pushes and adds no attempt; `INDEX_CONFLICT_ROUNDS` bounds our own replayed commits, not upstream's rate |
| A human README's hand text holds a seven-character marker line | screened before staging; the record publishes; warning on every push and INFO/WARN in the validator name the line; the gate's own hint ("indent or lengthen") is reused |

## Implementation notes (2026-10-02)

What was built differs from the sections above in the places below. The text above is left as written; this list is the record of where the implementation deliberately deviates, and why.

1. **`flatten` cuts, then escapes.** Component 1 and "Index format" list the two steps the other way round. The implementation cuts the one-line text at the last space at or after 40 characters (else hard) and escapes afterwards, so a cut can never split an escape sequence; the bytes differ from the spec's order only for a label over the limit that holds an escapable character.
2. **The malformed-markers detail carries the exception text.** `index.readme-stale` for malformed markers reports `markers malformed (<reason>)` — the kernel's own `MalformedMarkers` message (`expected one start and one end marker, found N and M`, `end marker precedes start marker`) — rather than the bare `markers malformed` of Component 8.
3. **`MalformedMarkers` also on duplicate pairs.** A README with more than one start or one end marker line is malformed too (Component 1 names start-without-end, end-without-start and out-of-order). A marker counts only as a whole line at column 0; the marker text inside a row, a heading or a sentence is prose and never counts.
4. **`lmer-schema index` output and refusals.** A refused file prints `refused   <rel> — <reason>` (plus a hint for `ignored`, `newer format` and `marker line in hand text`) with no `(+N -M)` delta; the delta appears on `create`, `update` and `unchanged` lines only, and `--json` reports `added`/`removed` as `0` for a refusal. The command also exits 2 on a `RegistryError` (a manifest whose `projects:` block breaks a rule), beside `ManifestError` and `OSError`. `--write` computes its plan — the tracked-filter snapshots and the record scans — inside `work_mutation(root)`, not before taking the lock.
5. **The root README is not screened for a hand-text marker line.** The choke point never stages the root README, so a setext `=======` in the root's hand text cannot trip the staged-marker gate: `lmer-schema index` writes the root block beneath such a line and refuses only a project README that holds one, and the validator reports the marker detail for project READMEs only (the root block is judged for malformed markers, a newer format token and staleness).
6. **`_git_raw` also runs with the pinned editor env.** Component 3 names `run_git_command`; the publication-index helper `_git_raw` builds its environment from the same `_GIT_BASE_ENV` (`LC_ALL=C`, `GIT_EDITOR=true`, `GIT_SEQUENCE_EDITOR=true`), so every git call `work_repo.git_ops` makes is covered. The kernel's read-only `git ls-files` (`project_index.tracked_record_filter`) sets `LC_ALL=C` only.
7. **`_apply_launch_identity` writes a copy first.** The function builds a candidate copy of the state, calls `write_state` with the copy, updates the caller's shared `state` only after that write succeeded, and appends the events last; a failed write therefore leaves the caller's later owner write with nothing new to persist and the record truthfully unnamed (Component 4 describes mutate-then-write).
8. **The delivered-env test uses `LMER_TASKDEF_PATHS`.** `tests/test_lmer_cli_local_target.py` points the host at its stub `chat` taskdef through `LMER_TASKDEF_PATHS` (the external taskdef root the host CLI documents), not `LMER_TASKDEF_ROOT` as the Testing strategy names it.
9. **The `read_state_fast` cut has extra guards.** Beyond the conditions in Component 1 (one column-0 `context:` line, a delimited block, the anchored `source_path` matched or absent), the cut is used only when every quoted scalar and flow collection opened above the line and inside the block closes there, when the matched `source_path` does not continue on a deeper-indented line (the emitter folds a long plain scalar at a space) and when it loads as a scalar; anything else falls back to the full parse. Parity with a full parse is pinned over chains, flow-style and context-less records.
10. **`display_state` accepts an ISO-string `now`.** The signature is `now: datetime | str | None`; `run_state.list_sessions` passes its own `utc_now_iso()` string straight through. An `updated` or `now` whose UTC conversion overflows the datetime range reads as unparseable (`open` under a clock), and an unhashable `status` (a hand-edited list or mapping) is never `closed` and never a `TypeError`.
11. **Out-of-range stamps in the kernel.** `_parse_stamp` and `_stamp` treat an `OverflowError` from the UTC conversion (year 1 with a positive offset, 9999 with a negative one) as unparseable: the raw text is rendered and sorted after parseable stamps, and an unquoted twin keeps the same spelling as its quoted one.
12. **The leftover sweep names its untracked mode.** `_dirty_index_rels` passes `--untracked-files=normal` to its porcelain call, so a checkout whose config says `status.showUntrackedFiles=no` still finds a tool-created leftover README.
13. **Issue #353 D20 in the kernel and the choke point.** `work_repo.project_index` takes the manifest's name from `work_repo.utils.MANIFEST_NAME` (the rendered root block is byte-identical), and `git_ops._index_project_rels` takes its project set from `work_repo.utils.work_repo_project_rels`, which holds the lazy `lmer_schema` imports — so `work_repo.utils` stays the one module in the work CLI that spells the manifest name and the schema package's import.
14. **`docs/INDEX.md` had no SCHEMA-V2 block to amend**; one was added beside the SCHEMA block, with the project index among its bullets.
15. **The examples are synthetic.** This document ships on the public mirror, so the Index format and path-mapping examples name synthetic projects, ids and `example.test` repositories, and the rollout and task-10 steps use placeholders (`<work-repo>`, `<project>`), rather than the first consumer's; the worked `work-notes/README.md` is the render `tests/test_work_repo_project_index.py` pins byte for byte. No design decision changed; consumer-specific rollout steps belong in that consumer's work repo.
16. **The index writers share a write boundary, and the root README is committed explicitly.** `work_repo.project_index.project_dir_refusal(root, rel)` holds every project directory to one boundary before either writer touches it. The root is resolved first, so a checkout reached through a symlink still indexes and publishes. A directory is refused when it resolves outside the resolved root (`project directory resolves outside the work repo`), when there is a `_runs` component between the root and the directory (`project directory lies inside a _runs/ record`), or when it is a symlink or lies below one (`project directory is a symlink` / `project directory lies below a symlink`). The walk's registered branch follows a symlinked short name (`is_dir()`), and the kernel's README check sees only the final file, so without the boundary an alias carried the write outside the tree or into a completed record. The `lmer-schema index` planner reports the reason as `refused` (exit 1, preview and `--write` alike). The choke point's `_refresh_project_indexes` skips with `⚠️  project index skipped:` before any git call. The leftover sweep names the README with `⚠️  project index leftover skipped:`: a tracked project dir later replaced by a symlink is listed by `git status` as deleted. The CLI surface's "`lmer-schema index /work --write` followed by `work commit` is the in-container rebuild" holds for project READMEs only. No push stages the root README, which stays off the hot path, so a `--write` that wrote the root ends its summary with `not committed — commit the root README.md explicitly through the normal gated commit (work commit publishes project READMEs only)` instead of the `work commit` tail. The documented backfill commits the root explicitly.
