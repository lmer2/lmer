# Release Flow — GitLab-Driven, Read-Only GitHub

How a public release ships: development and release decisions live on the
canonical GitLab instance, GitHub is a publish target that runs the PyPI
upload, and the
whole sequence is a tracked lmer run with durable state, receipts, and
resume semantics. This document is the canonical explanation of the flow —
the topology, the two legs, the watch/resume contract, the signing model
and its honest limits, and the error paths.

## 1. Topology — canonical and mirror

**The GitLab instance is canonical.** All development, MRs, and release
decisions happen there. The GitHub repository (`github.com/lmer2/lmer`) is a
**mirror** in the strictest sense: a publish target that receives exactly
two kinds of writes — `main`, and SSH-signed `v*` tags — and nothing else.

- No PRs. The mirror does not accept pull requests; contribution happens on
  the canonical repo.
- No direct human or agent pushes. The only writer is the release taskdef's
  bot credential, and only during a release run.
- No sync branches. `main` on the mirror is a fast-forward image of
  canonical `main`; divergence is a hard stop, never a force-push.

The mirror exists because publishing to PyPI stays tokenless: GitHub
Actions on the mirrored tag performs the upload via trusted publishing
(OIDC), with PEP 740 attestations generated by default. The trigger lives
on the mirror, but the decision never does.

Tag convention is `v*` on both remotes, and the tag name is always derived
from `pyproject.toml` **at the tagged commit** — never from an earlier
step's memory.

## 2. The release run — one run, two legs

A release is a tracked lmer run owned by the `release` taskdef. Run state
records every transition; every externally visible step leaves a receipt.
The run has two legs with a human gate between them.

### Leg 1 — prep (GitLab side)

1. Branch off `prep-release`.
2. Run ctl to bump the version and roll the changelog (mechanism is a
   per-repo parameter: `changelog.d/` fragments where adopted, legacy
   `CHANGELOG.yaml` roll otherwise). A dry-run validates the changelog mode
   before anything is committed.
3. Commit, push, open an MR targeting `prep-release`.
4. Once the bump MR lands, the standing `prep-release` → `main` MR **is**
   the release MR. **Record in run state:** the release version and the
   bump-MR merge SHA.

### The gate — human merge

The run arms the `--check-updates --watch` primitive on the release MR and
idles with pushed state. The human merging the protected-`main` release MR
on the canonical GitLab instance is the release approval — that merge is the
procedural
trust anchor for everything that follows.

### Leg 2 — ship

On merge detection:

1. **Record the merge SHA** of the release MR into run state. All
   subsequent steps key on it. Read the release version from
   `pyproject.toml` at that SHA; it must match Leg 1's recorded version.
   A mismatch means a second bump or a foreign commit landed — hard stop,
   human decision required.
2. **Preconditions**, each recorded as a receipt:
   - The GitLab `main` pipeline at the merge SHA is green.
   - GitHub `main` is an ancestor of the merge SHA (any divergence is a
     hard stop with a documented remediation path, never a force-push).
3. Create an **SSH-signed** tag `vX.Y.Z` at exactly the merge SHA
   (`git tag -s`, release signing key).
4. Push to **GitHub — `main` first, then the tag**. The ordering matters:
   the tag push triggers the release workflow, and the verify job asserts
   the tag equals `main` HEAD, so `main` must land before the trigger
   fires. Poll the Actions release run to completion. Green means PyPI has
   the version (with attestations) and the GitHub Release exists. Red
   means fail loudly with the Actions run URL — and at this point nothing
   has been published internally yet.
5. **Only after GitHub is green**, push the tag to GitLab origin, whose
   tag pipeline publishes the internal package registry and container
   image. Public-before-internal ordering means a GitHub failure leaves no
   half-released internal state — the flow cannot silently drift into
   "released internally but not publicly" or the reverse.
6. Record receipts (verification events, Actions run URL, PyPI URL) and
   complete the run.

## 3. Watch, resume, single-flight, idempotency

**Watch is best-effort; run state is the contract.** The watcher session
that idles across the human gate can die — container reaped, host
rebooted — and nothing is lost. Relaunching the release taskdef is a
**resume**: it re-derives the current leg from run state (bump merged?
release MR merged? tag created? pushed where?) and continues from there. A
merge that happens while nothing is watching is picked up at the next
launch. The relaunch is scheduled — a periodic launch of the release
taskdef runs while a release is in progress and exits immediately when
there is nothing to advance — so a merged release MR never sits untagged
longer than one schedule interval. Manual relaunch works identically.

**Single-flight.** At most one active release run per repo. The lock is
the run-state layer's **atomic run claim** (owner/claim recorded in
`state.yaml` by the single-writer `work` CLI), not a check-then-create in
the taskdef — two simultaneous launches cannot both win. A second launch
refuses to start and points at the active run. This rule is also what
keeps Leg 2 convergent: no other release advances GitHub `main` while this
run is incomplete, so the tag-at-`main`-head assertion stays satisfiable
across re-runs; only an out-of-band manual push could break it.

**One release, one run — release-run identity.** Run identity is derived
from `(taskdef, target)`, which is the same string for every release of a
repository. A release run therefore moves to a **version-bearing address**
as soon as leg 1 records the version — `release-<repo>` becomes
`release-<repo>-v0.6.0` — and the address it vacates is where the next
release seeds. Nothing has to know the version at launch: the run resolves
by content, so a scheduled or manual relaunch still lands on the in-flight
release, and `work release claim` rolls a finished run aside (and seeds its
successor in the same atomic commit) if one is still parked on the seed
address. Without this a repository could release exactly once — the second
release resolved to the first's finished run and was refused permanently.
Full mechanics: `docs/RUN-STATE.md` §7.

**Idempotency, precisely.** Every step checks against the recorded merge
SHA and version before acting:

- Tag exists → verify it points at the recorded SHA and carries a valid
  signature. Pointing anywhere else is a hard error — never re-point,
  never re-sign.
- GitHub refs current → skip the push.
- Actions already green for the tag → skip the poll.
- **Actions red with refs current → re-dispatch the workflow via the API
  (workflow re-run), keyed on the recorded SHA.** A re-entered Leg 2 must
  be able to converge after a transient failure, not just re-observe the
  red run.
- Leg 1 is idempotent against an aborted predecessor: if a prior run
  bumped the version on `prep-release` and was then abandoned, the next
  run's ctl dry-run detects the bump and roll already in place, skips
  them, and resumes from the release-MR/watch step.

## 4. Signing and verification — the honest threat model

**What the signature is:** a provenance marker binding the tag to the
sanctioned release tooling, plus a bypass-resistant-as-practical
verification gate on the publish path. **What it is not:** a boundary that
survives compromise of the release credentials themselves — the signing
key and the GitHub PAT are provisioned into the same release session, so a
fully hijacked release session holds both. The real perimeter is
credential custody plus GitHub repo controls; the signature narrows the
attack surface from "anyone with any write path" to "holder of the release
credentials".

Mechanics:

- A dedicated **release SSH signing key**, provisioned only to
  release-taskdef sessions. Tags are created with `git tag -s`. Sessions
  of any other taskdef never receive the key or the PAT — that negative
  guarantee is tested, not assumed.
- The release workflow's **first job verifies the tag**, with the trust
  anchors kept **out of repo content**. This matters because a workflow
  run on a tag executes the workflow from the tag's own tree — anything
  committed to the repo can be altered by whoever pushes a tag:
  - The expected signer public key is pinned in an admin-controlled GitHub
    Actions repository variable, `vars.RELEASE_ALLOWED_SIGNERS`, not in a
    checked-in file.
  - The verify job's **checkout is pinned to `main`**, so the verification
    script itself never comes from the tag's tree either. The workflow
    *definition* still rides the tag ref — that residual is bounded by the
    tag ruleset and PAT custody below, and the pin trims the tag-borne
    attack surface to the workflow text alone.
  - The job asserts the tag commit **equals the head of GitHub `main`**,
    fetched from the API rather than read from the tag's tree.
  - Signature invalid or absent, or tag not at `main` head → the pipeline
    fails → nothing publishes.
- The **PyPI trusted publisher registration is pinned** to the repo, the
  workflow path, and the `pypi` environment.
- The `pypi` environment carries a **deployment tag-pattern policy**
  narrowing which refs may deploy. Without protection rules, an
  unprotected environment can be requested by any workflow in the repo —
  a tag-borne workflow could simply declare `environment: pypi` — so the
  environment binding alone does not survive credential compromise.
- The human trust anchor remains the protected-`main` MR approval on
  GitLab (procedural, recorded by GitLab).

**Residual risk, stated plainly.** The release PAT is fine-grained but
carries `contents:write` + `workflows:write` on the mirror (the workflows
scope is required: mirrored `main` routinely carries
`.github/workflows/*` changes, and GitHub rejects workflow-touching pushes
without it). An attacker holding that PAT can rewrite `main`, workflows,
and tags together, defeating all in-repo and variable-based checks. With
the deployment tag-pattern policy in place, the remaining exposure under
PAT compromise is **accepted**. Mitigations are custody (release sessions
only), minimal collaborators on the mirror, tag protection, and PAT
expiry. One hardening option is deliberately deferred: a required-reviewer
rule on the `pypi` environment would add a one-click human approval on
GitHub per release and is the only control here that fully survives PAT
compromise — it trades away the hands-off flow, and remains available if
that trade ever changes.

Out of scope, chartered as its own future project: self-hosted sigstore
(Fulcio/Rekor) for keyless signing from the canonical GitLab instance — the
public Fulcio CA does not trust self-managed GitLab as an OIDC issuer.

> **Note — why the residual risk is published here.** This directory is
> mirrored to the public GitHub repo, so this section is, deliberately, a
> public statement of where the flow's boundary sits. The full
> residual-risk detail stays in this public doc rather than being
> summarized here and hidden in a private charter. Rationale: every fact
> above is standard GitHub mechanics that an attacker holding the PAT
> could derive in minutes — omitting it would be security through
> obscurity, while publishing it lets adopters and auditors evaluate the
> design honestly. What stays private is operational, not architectural:
> credential custody paths, rotation runbooks, and provisioning specifics
> live in the private work repo.

## 5. PyPI publish semantics — `skip-existing` and re-run drift

The PyPI publish step in the release workflow sets `skip-existing: true`
so a re-run after a partial failure (uploaded to PyPI, died before the
GitHub Release step) converges instead of failing on "file already
exists".

That convergence is never silent, and never automatic: a version-reuse
gate (`.github/scripts/gate-version-reuse.py`) runs before the publish
step, querying the index's JSON API for the tag's version.

- **Version not on the index** — first publish, proceed.
- **Version present, holding an artifact this run did not build** — fail
  before publish. Never publish over a diverged release.
- **Version present with exactly this run's filenames** — fail, unless the
  `RELEASE_RESUME_VERSION` Actions repository **variable** names that exact
  version. Then the run proceeds with a warning, and `skip-existing`
  no-ops the overlap.

The reason the last case fails by default is that it is genuinely
ambiguous. Distribution filenames are a pure function of (project name,
version), so a resumed publish and a *republish of different code under
the same version* produce byte-for-byte identical file lists. Digests
cannot separate them either — the build is not bit-reproducible, so a
legitimate re-run's artifacts differ from what the index holds — and PEP
740 provenance binds the artifact to its run inside the signing
certificate, not in the JSON the index API serves. Since the gate cannot
tell the two apart, it refuses and asks a human: an admin sets
`RELEASE_RESUME_VERSION` to the version being resumed, re-runs the
workflow, and clears the variable afterwards. Same trust model as
`RELEASE_ALLOWED_SIGNERS` — an admin-controlled Actions variable, never
repo content, never a secret. The gate logs both sides' filenames,
sha256 digests, upload times and provenance URLs, so the decision is made
against evidence.

The gate script itself is checked out from `main`, never from the pushed
tag: the publish job holds `id-token: write`, so nothing running in it may
come from the tree being published (the same rule the tag-verification job
follows).

That leaves the residual caveat: on an authorized resume the upload is
skipped, so the **attestations from the re-run are not what PyPI
serves**. For this reason, receipts record **which Actions run actually
uploaded**, and the last green run URL is never over-trusted as the
provenance of the published artifact.

## 6. Error paths

- **Tag/version mismatch:** the workflow's verify-version job requires tag
  `vX.Y.Z` to equal `pyproject.toml` at the tag.
- **GitHub publish failure:** the run reports the Actions run URL and
  fails. Re-running Leg 2 converges (idempotency + `skip-existing`) —
  unless the version already published, where the reuse gate (§5) stops
  the re-run until an admin authorizes it via `RELEASE_RESUME_VERSION`.
  No silent success either way.
- **Burned version:** PyPI filenames are permanent — once an upload
  succeeds for a version, that version is spent even if yanked. Repair is
  a yank (if warranted) plus a new patch version through the same flow;
  tags are never deleted or re-pointed.
- **GitHub `main` divergence** (non-fast-forward push): hard stop.
  Remediation is a human decision recorded in the run — never an
  automatic force-push.
- **Watch death / session loss:** run state is pushed at each transition;
  a relaunch resumes at the derived leg (§3).
- **GitHub push rejected** (e.g. a read-only token on the push path): hard
  error naming the credential requirement; never fall back to an
  alternative push path.
- **Concurrent releases:** excluded by the single-flight rule (§3).
- **Abort / abandoned release:** a release can die after Leg 1 (bump
  merged to `prep-release`, human declines the release MR). Aborting is
  explicit: the run is marked aborted, releasing the single-flight lock;
  the bump commit stays on `prep-release`, and the next release run's
  dry-run detects and skips it (§3). An aborted run is **terminal** — it
  is never re-claimed as itself, and that next release run is a NEW run
  (§3, release-run identity). `work release abort` refuses while a **live
  foreign** claim holds the run (another session is mid-release) unless
  `--force`; a stale claim clears without it.
  Because the bump is skipped rather than redone, **the successor records
  the same `X.Y.Z` as the run that was declined** — and the declined run is
  already parked on `release-<repo>-v<X.Y.Z>`, since the decline happens at
  the release-MR gate, after Leg 1 recorded the version. The successor
  therefore takes a uniquified address (`…-v<X.Y.Z>-<stamp>`) rather than
  keeping the seed address; see RUN-STATE.md §7, where one-slug-names-one-run
  is the invariant that makes this safe.
- **Re-run artifact drift:** the `skip-existing` caveat in §5 — receipts
  identify the uploading run, not merely the latest green one.

## 7. First production release — deferred with handoff

The build that produced this flow ships the machinery and the rehearsal
harness; it does not itself perform a production release. The first
production release of lmer end-to-end through the flow — the build's G4
goal — is **deferred with handoff**: it executes as a follow-on,
human-gated release run launched with the shipped `release` taskdef, not
as part of the build, because it requires the human release-MR merge
(§2's gate) and production credentials that only release-taskdef sessions
ever hold (§4).

### Prerequisites

All of the following must hold before launching the run:

- **The build is complete and green** — every deliverable of the flow
  (taskdef, workflow, rehearsal rig, docs) shipped.
- **Rehearsal evidence recorded and verified** — the G2 negative test and
  the leg-2 dry run, per the standing rule in
  [RELEASE-REHEARSAL.md](./RELEASE-REHEARSAL.md): both aggregate evidence
  files in `docs/rehearsal/` populated from real run data and passing
  their offline verifiers. The files ship as pending skeletons and are
  populated when the rig runs — a pending skeleton is not evidence.
  Waiving this for a given release is possible but must be **recorded in
  [RELEASE-PROD-SETUP.md](./RELEASE-PROD-SETUP.md) with its rationale and
  accepted residual** — an unrecorded skip is not a waiver.
- **Gating operator receipts complete** — every item in the *gating*
  section of [RELEASE-PROD-SETUP.md](./RELEASE-PROD-SETUP.md) ticked with
  date and actor. A release run must refuse to proceed to Leg 2 while any
  gating item is unchecked. That file's **hardening** section does not
  gate: those items close real holes but a release completes correctly
  without them, and they are tracked separately so an open hardening task
  cannot block a release — nor pass unnoticed.

### Procedure

Launch the `release` taskdef for lmer. The run proceeds exactly as §2
describes — Leg 1 prep, the human gate, Leg 2 ship — with no
first-release special casing (legacy changelog mode is acceptable for the
first release, per the taskdef's per-repo changelog parameter).

### Closure

The release run's receipts — the gate and verification events from run
state, the Actions run URL, the PyPI project page — are recorded back
into the build's goal assessment as its G4 evidence. The receipts
themselves live where they were produced: the completed operator template
in [RELEASE-PROD-SETUP.md](./RELEASE-PROD-SETUP.md) and the release run's
own run directory in the work repo. The handoff closes when that evidence
is in place; until then, G4 remains open by design — deferred, not
dropped.
